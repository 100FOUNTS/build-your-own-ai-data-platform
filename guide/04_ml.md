# Module 4 — Machine learning: two models, experiments and a champion

⏱ 5–6 h · Services: `make up-db up-lake` (MLflow on :5001) · Check: `make check-4`
**Tools:** NumPy, pandas, scikit-learn, **PyTorch**, **MLflow**.

## What you will build
`python -m ml.train`: reads the `asset_daily_features` table (gold), trains **two models** that predict “will this pump fail within 7 days?” —a classic one
(scikit-learn) and a **PyTorch autoencoder** (it learns what *healthy* looks like; the reconstruction error is the anomaly score)—, logs
both as **experiments in MLflow**, promotes the best one to **champion** in the model registry and publishes each pump's risk for each day to the
Postgres `risk_scores` table (that is where the API reads it from).

## Why this module exists
Training a model is the easy part; the hard part is making it **reproducible, comparable and deployable**. MLflow solves the first (which data, which
params, which metric each run gave) and the model registry the second (which version is in production today). And honest evaluation
—the gap between training and test, the right metric for imbalanced classes— decides whether the 0.8 you report means anything.

Two models because comparing is the best way to understand a problem: does the supervised model, which sees the labels, win, or the autoencoder, which
only sees healthy data? In practice, the autoencoder is useful when there are **few labeled failures** (here there are 16 in 90 days).

## Concepts
- **Time split with purging**: you train on the past, test on the future and leave a gap of ≥ 7 days (the label looks 7 days ahead). Never random.
- **Average precision (AP)** and the **baseline**: with ~8% positives, chance gives AP ≈ 0.08. An AP of 0.5 is six times better.
- **Autoencoder**: a neural network that compresses the input and reconstructs it. Trained only on healthy data, it reconstructs the abnormal badly.
- **Experiment / run**: one execution with its params, metrics and artifacts. **Model registry**: versions with **aliases** (`champion`).
- **Scoring “today”**: you also have to predict the last days, which **have no label** (the future hasn't happened).
- **Idempotency again**: retraining must not duplicate rows in `risk_scores` (UPSERT).

## The contract
**Running**: `python -m ml.train`. Environment: `WAREHOUSE_PATH` (DuckDB with `asset_daily_features`), `MLFLOW_TRACKING_URI`, `MLFLOW_EXPERIMENT` (default `pump-risk`),
`MODEL_NAME` (default `pump-risk`), `DATABASE_URL`.

**In MLflow** (experiment `MLFLOW_EXPERIMENT`): ≥ 2 finished runs with
- params `model_type` (`sklearn` and `autoencoder`), `train_end`, `test_start` (gap ≥ 7 days);
- metrics `average_precision` and `baseline_average_precision` (share of positives in test);
- for the autoencoder, the `train_loss` metric **per epoch** (≥ 5 points, decreasing).

**Registry**: model `MODEL_NAME` with the alias **`champion`** pointing to the run with the highest AP, which must reach **≥ max(0.25, 3 × baseline)**.

**In Postgres** (`risk_scores`, module 1): one row for every gold row (**including the last days without a label**), `risk_score ∈ [0,1]`, `model_version`
identifies the champion. Rerunning is safe.

## Your task
1. Load gold with pandas/DuckDB and **look at it**: how many positives are there? which columns are features and which are NOT (keys, label)?
2. Define the time split (test ≈ 25 days, gap ≥ 7). Write it down in `notes/`.
3. Train the scikit-learn model (e.g. `HistGradientBoostingClassifier`, which tolerates nulls). Measure AP on test against the baseline.
4. Train the autoencoder with PyTorch **only on healthy training rows** (fill nulls, standardize with the train mean/std). Score with the reconstruction error normalized to [0,1].
5. Log everything in MLflow (`mlflow.start_run`, `log_params`, `log_metric(..., step=epoch)`, `log_model`). Open http://localhost:5001 and compare the runs with your own eyes.
6. Register the best model (`mlflow.register_model`) and assign the `champion` alias.
7. Score **all** the rows and UPSERT them into `risk_scores`.

## How you will know you are done
`make check-4` builds a gold table with an independent computation (so it doesn't depend on your module 3 being perfect), runs your training against a temporary
Postgres database and a new MLflow experiment, and reviews experiments, params, the loss curve, the champion alias, the minimum AP and the published rows.

## Hints
<details><summary>MLflow 3 refuses to save my sklearn model</summary>

MLflow 3 serializes with `skops` and rejects untrusted types (HistGradientBoosting). Look at the `serialization_format` option of `mlflow.sklearn.log_model` and understand the security trade-off it implies.
</details>
<details><summary>PyTorch in MLflow asks for an input example</summary>

The default format exports the graph and needs `input_example` (a NumPy array with the shape of one input).
</details>
<details><summary>The AE has a low AP</summary>

Standardize the features with *training* statistics, impute nulls with the training median and normalize the error with percentiles of the healthy rows (e.g. p50→0, p99→1). A smaller autoencoder usually works better with 13 features.
</details>
<details><summary>Registering and setting the alias</summary>

`mv = mlflow.register_model(f"runs:/{run_id}/model", name)` and `MlflowClient().set_registered_model_alias(name, "champion", mv.version)`.
</details>

## Common traps
- Including `label_failure_7d` or the keys among the features.
- Standardizing with statistics from the **whole** set (leakage into the test).
- Picking the champion by *training* AP, or looking at the test to tune hyperparameters (the test “gets used up”).
- Scoring only the labeled rows and forgetting the last days, which are what matters “today”.
- A plain `INSERT` into `risk_scores` (the second run fails on a duplicate key).
